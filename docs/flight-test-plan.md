# 비행시험 기록·비교 구현 계획

2026-11-17 사용자 요청에 따른 다음 작업 계획이다. 아래는 승인한 원래 구현 계획이며, 후속 구현과 실제 결과는 [비행시험 사용법·기록](flight-tests.md)에 별도로 기록한다. 현재 연구 모델과 기존 검사 결과는 [C208B 연구 안내](c208b-research.md), [확장 진행](fixed-wing-expansion.md)을 따른다.

목표는 같은 초기 조건과 입력을 반복하고, 상태·명령·실제 작동기 출력을 기록하여 연구 가정의 영향을 비교하는 것이다. 첫 완료 단위는 **C208B 65m/s 수평 트림의 엘리베이터 짧은 입력 시험 한 개와 CSV·그래프·판정**이다. 이후 시험 종류와 한 매개변수의 민감도 비교로 넓힌다. 실기체 성능 검증·계수 식별 완료로 표현하지 않는다.

## 현재 있는 것과 재사용할 것

- `uavsim_client.py`: 상태·수동 입력·reset·일시정지·명시적 step·바람/고장·플랩·항로 API. 기록기는 이 공개 API만 사용한다. Unreal Remote Control에 직접 의존하지 않는다.
- `tests/research_checks.cpp`: 연구 JSON 수치, 트림·수동 응답 방향·동력 상한·플랩·고정기어·자동 운항 검사. 여기에 필요한 수치 검사를 보강한다.
- `tests/fixed_wing_checks.cpp`, `tests/systems_checks.cpp`: 독립적인 조종 미계수 응답과 작동기 해석해가 있다. 같은 검사를 새 파일에 복제하지 않는다.
- `scripts/check-c208b-api.py`: 실제 API 시험과 파일·바람 복구 패턴이 있다. 기록 도구는 기존 성공 횟수 집계보다 시간 이력과 근거를 중심으로 만든다.
- 별도 계획 수립 당시 시계열 기록·겹쳐 보는 그래프 도구는 없었다. 새 서버·대시보드·플러그인은 만들지 않는다.

## 작업 범위

| 포함 | 제외 |
| --- | --- |
| 카메라 크기 대응 수정의 빌드·적용 마감 | 카메라 조작 UI 개편, CCD/짐벌 변경 |
| 기존 API를 호출하는 명령행 시험·CSV/JSON 기록 | 새 통신 방식, 실시간 스트리밍 서버, 범용 시험 DSL |
| 저장 기록에서 정적 SVG/PNG 그래프와 HTML 보고서 생성 | 라이브 대시보드, Web UI 차트 확장, 직접 만드는 차트 엔진 |
| 트림·종/횡 입력·선회·엔진컷·플랩 시험 | 새 기체, 센서/FCC, 지형·DTED·워게임 확장 |
| 선언한 연구 매개변수를 한 번에 하나씩 바꿔 비교 | 자동 계수 튜닝, 실측 없는 성능 맞추기, 불확도 확률분포 추정 |

기록·검증·HTML은 Python 표준 라이브러리 `csv`, `json`, `hashlib`, `html`, `argparse`를 사용한다. 과학적 그래프는 Matplotlib의 비대화형 백엔드로 SVG/PNG 독립 파일을 만든다. 현재 엔진 번들 Python에는 Matplotlib이 없어, 구현 단계에서 프로젝트 전용 Python 환경에 그래프용 의존성 한 개만 버전을 고정한다. 엔진 번들 환경은 수정하지 않는다. 축·범례·단위·눈금 처리를 직접 구현하는 차트 엔진은 만들지 않는다.

## 0. 카메라 수정 마감

현재 실행에는 메인 카메라 뒤47.55m·위14.265m를 API로 적용했다. `FlightScene.cpp`의 표시 날개폭 기반 배치 수정은 아직 빌드하지 않았다.

시험 실행을 위해 비행을 정지·초기화하는 시점에 해당 모듈을 빌드하고 API가 관리하는 독립 창만 정상 재시작한다. 사용자가 별도로 연 에디터는 종료하지 않는다. C208B의47.55m/14.265m, Thor의 기존6m/1.8m 배치와 시점 전환 후 복귀·프로필 재읽기 후 갱신을 실제 속성으로 확인한다. CCD 모드·FOV·짐벌 설정 유지도 확인한다. 카메라 자체의 화면 만족도는 사용자의 현재 확인을 기준으로 삼고 UI 자동화는 하지 않는다.

**완료:** 카메라 소스가 실제 빌드에 포함되고 기본/전환 시점에 적용된다. 이 변경만으로 계산 코어 전체 검사를 반복하지 않는다.

## 1. 첫 시험: 엘리베이터 짧은 입력

시험 조건은 다음처럼 고정한다. 숫자는 재현 가능한 작은 교란을 위한 **개발 시험 설정**이며 실제 C208B 시험 절차나 안전 한계가 아니다.

| 항목 | 첫 시험 조건 |
| --- | --- |
| 기체 | `c208b-research.json`, 원본 바이트와 적용 fingerprint 확인 |
| 초기 상태 | 원점 위도·경도와 함께 WGS84 타원체고2600m, TAS65m/s, 북향 수평 트림 |
| 환경 | 무풍·돌풍 없음·정상 출력·조종면 고착 없음 |
| 형상·제어 | 기어 전개, 플랩0°, 자동항법/자동 운항 해제 |
| 트림 입력 | 초기화 결과의 실제 트림 명령을 읽어 사용. 스로틀.5나 엘리베이터0으로 덮어쓰지 않음 |
| 시간 | 시뮬레이션 총30초. 0~5초 트림 유지, 5~5.5초 트림 대비 엘리베이터+1°, 5.5~30초 트림 명령 복귀 |
| 적분·기록 | API `step(.02)` 뒤 반환 상태를50Hz로 기록. t=0도 저장, 총1501행. 입력 이벤트는 정수 샘플 번호250/275에서 적용 |

양의 엘리베이터는 trailing edge down이며 현재 모델의 음의 Cmδe에 따라 초기에 nose-down 모멘트를 만든다. 명령각 변화와 실제각 변화 사이의 서보 지연을 보존한다. 다른 조종면·스로틀은 트림 값을 유지한다. 실행 중 자동조종이 다시 활성화되거나 기체 fingerprint가 바뀌면 시험을 중단한다.

기존 API에서 `step`은 배속과 무관한 시뮬레이션 시간이다. 벽시계50Hz 타이머나 sleep으로 입력을 스케줄링하지 않는다. HTTP가 느려도 샘플을 건너뛰지 않는다. 총 실행 시간은 계측하고 초당 요청 성능을 보장하지 않는다.

**완료:** 첫 명령 한 번으로 시험·저장·정적 보고서 생성까지 성공하고, 잘못된 초기 조건·API 실패·NaN을 성공으로 기록하지 않는다. 첫 결과를 검토하기 전 다른 종류의 시험이나 계수 변경으로 넓히지 않는다.

## 2. 기록·오류·파일 계약

구현할 파일은 `scripts/run-flight-test.py`와 `scripts/report-flight-test.py` 두 개로 시작한다. 첫 번째는 API 실행·저장, 두 번째는 API 연결 없이 저장 자료를 읽어 그래프·비교 보고서를 만든다. CLI 입력 검증은 각 도구에 두고 작은 공용 프레임워크를 추가하지 않는다.

산출물은 고유한 실행 폴더 `artifacts/flight-tests/<run-id>/`에 둔다. 기존 실행 폴더를 덮어쓰지 않는다.

| 파일 | 내용 |
| --- | --- |
| `metadata.json` | 기록 형식 버전, 시험 종류·이벤트 일정·dt·초기 조건, 축/단위, 기체 ID·적용 fingerprint·프로필 SHA256, 실행 시각·실제 소요 시간, 관련 소스/모듈 지문과 확보 여부 |
| `profile.json` | 실제 사용 프로필의 원본 사본. 수치·출처·개발 가정을 함께 보존 |
| `samples.csv` | 시뮬레이션 시간, 위치/자세·TAS/지상속도·수직속도·alpha/beta·p/q/r·하중배수·분리율, 명령/실제 조종면·스로틀, 추력·플랩·기어, 운항 모드·fault |
| `result.json` | 시험 상태·검사 항목·실패 이유·실패 시각·최종 상태·복구 결과·지표, 판단 근거가 없는 항목은 미판정 |
| `report.html`, `response.svg`, `response.png` | 입력/출력/자세/속도/고도 시간 이력. profile·조건·미검증 경고를 명시 |

각 열 이름에 `_s`, `_m`, `_mps`, `_deg`, `_deg_s`, `_n` 등 단위를 넣는다. 위치 높이는 WGS84 타원체고, 자세 heading은 북 기준 시계방향, 각속도는 body FRD다. alpha와 pitch, TAS와 지상속도, 명령과 실제각을 구분한다. API에 없는 ENU 속도/힘·모멘트를 추정하여 실측 열처럼 채우지 않는다. 에너지·모멘트 검사는 해당 값을 직접 얻는 코어에서 수행한다.

실패 시에도 마지막 수신 행·fault·HTTP 오류·메타데이터를 남긴다. 시뮬레이션 시간의 단조 증가·예상 dt·행 수·유한값을 검사한다. 타임아웃 난 mutation은 자동 재시도하지 않는다. 판정 실패/실행 오류/복구 오류는 모두 0이 아닌 종료 코드다. 불완전한 기록에는 성공/완료 표시를 하지 않는다.

진행 중 비행에서 일반 시험 명령은 기본적으로 거부한다. 별도 `--reset-flight` 옵션은 현재 비행을 시험 초기 조건으로 교체한다는 명시적 선택이다. **현재 API는 전체 내부 상태 snapshot/복원을 제공하지 않는다.** 종료 후 이전 비행 시간·각속도·항로 제어기 메모리까지 복원했다고 주장하지 않는다. 설정·선택 파일을 변경했다면 바이트를 복원하고, 기존 일정 바람과 기체를 복구한 공중 트림·정지로 끝내며 그 결과를 기록한다. 연결이 끊기면 복구 미확인 상태를 명시한다. 시험과 무관한 CCD/표적/워게임 상태는 변경하지 않는다.

## 3. 판정과 첫 기준 기록

한 실행의 시간 이력 저장이 끝나면 **같은 실행 파일·프로필·초기 조건·입력 일정으로 두 번** 실행한다. wall-clock/run-id 같은 메타데이터는 제외하고 시뮬레이션 열을 비교한다. 같은 환경의 완전 일치를 먼저 확인하고, 다르면 첫 차이의 시간·필드를 원인 조사한다. 플랫폼이 다른 실행의 bitwise 일치까지 약속하지 않는다.

| 검사 | 근거·판정 방식 |
| --- | --- |
| 초기 트림 | 기존 코어의 힘/모멘트 잔차·조종 한계 검사 재사용. API의 시작 속도만 보고 평형이라 판정하지 않음 |
| 서보 지연 | 기존 1차/속도 제한 해석해를 사용. 실제 조종면 응답을 명령각과 혼동하지 않음 |
| 초기에 작용하는 피칭 모멘트 | 동일 frozen state·실제각 변화에서 ΔM=q̄Sc Cmδe Δδe, Δqdot=ΔM/Iy를 독립 계산. 기존 Thor 미계수 검사 패턴을 연구 모델에 필요한 만큼 확장 |
| 동적 방향 | 실제 조종면이 움직인 짧은 구간의 종응답 방향을 확인. 30초 뒤 원래 고도/속도로 복귀한다는 조건은 두지 않음 |
| 적분 간격 영향 | 코어에서 실제 호출 간격 .01/.005/.0025초로 동일 이벤트를 적용하고 공통 시각에서 비교. API 기록 간격 .02→.01만 바꾸는 것은 내부 .01초 적분의 수렴 시험이 아님 |
| 재현 | 동일 환경의 두 기록을 비교하고, 허용오차를 늘려 재현 실패를 숨기지 않음 |
| 시간 이력 차이 | 같은 단위별 최대 절대 차이·RMS, 피치율/alpha 최대값·발생 시각, 속도/고도 변화량을 산출 |

기존 해석 검사 허용오차는 재사용한다. 새 수치 비교는 배정밀도 규모·기록 정밀도·간격 축소 결과로 허용오차 근거를 먼저 남긴다. 정확한 실기체 주기/감쇠율·최대 상승률·활공비를 임의 합격 기준으로 만들지 않는다. 감쇠나 충분한 진동이 관측되지 않으면 감쇠율/주기를 억지로 맞추지 않고 미산출로 둔다.

첫 성공 결과를 명시적으로 기준 기록으로 지정한다. 이후 매 실행 결과가 기준을 자동 덮어쓰지 않는다. 프로필이 달라지면 회귀 실패와 의도적인 민감도 실험을 구분한다.

## 4. 시험 종류 확장

첫 시험의 기록·재현·판정이 끝난 뒤 같은 파일 형식과 실행 흐름을 재사용한다.

| 순서 | 시험 | 확인할 내용 |
| --- | --- | --- |
| 4-1 | 무입력 트림 유지 | 선언한 조건의 속도·높이·각속도 변화와 잔차. 장시간 안정성을 실측 검증으로 표현하지 않음 |
| 4-2 | 엘리베이터 ±1° 짧은 입력 | 부호·서보 응답·종운동. ±응답이 완전 대칭이어야 한다고 강제하지 않음 |
| 4-3 | 에일러론·러더 각각 짧은 입력 | 롤/요 응답, beta·교차 관성 영향. 입력 한 종류씩 수행 |
| 4-4 | 기체별 항로·최종 선회 | 기존 자동조종으로 선회. 목표/실제 뱅크·속도·반경을 비교하고 무풍 준정상 구간에서 R≈V²/(g tanφ) 관계 확인. 수동 공력 응답 시험과 분리 |
| 4-5 | 엔진컷 활공 | 출력 고장=0과 스로틀 명령0의 차이를 구분. 전자는 즉시 추력 상실, 후자는 기존 스풀 응답을 따름. 속도·수직속도·고도 변화 기록, 실제 최적 활공 성능 주장은 안 함 |
| 4-6 | 플랩 전개/복귀 | 실제각·전개율·트림 교란·공력 변화. 상승/감속 방향을 순간값 하나로 단정하지 않음 |

각 시험마다 입력 크기·구간·지속 시간·지원 범위를 먼저 고정하고 기록한다. 엘리베이터 시험에서 선택한 .5초를 모든 축/운용에 무조건 복사하지 않는다. 범위 밖·crash/fault면 실패로 종료한다. 실제 지형 저공 왕복·이착륙은 이번 기록 기능의 필수 확장 시험에 포함하지 않고 기존 운항 검사로 남긴다.

## 5. 연구 가정 민감도 비교

같은 시험에 한 매개변수만 바꾸는 실험을 지원한다. 원본 프로필을 덮어쓰지 않고 provenance가 있는 임시 연구 프로필을 기존 재읽기 API로 적용한다. 원본/변형 SHA256·변경 항목·단위·변경 이유를 보고서에 기록한다.

첫 비교는 가정 관성 `iy`의 기준 대비±10%다. 이는 **실제 관성 불확도 구간이 아니라 반응을 살피는 임의의 개발 교란 폭**이다. 모든 변형은 기존 관성 정부호/삼각 조건·트림 검사를 통과해야 한다. 실패하면 시험 실패로 남기고 관성을 다른 항목과 함께 몰래 보정하지 않는다. 조건이 고정된 frozen-state Δqdot의 역관성 관계와 전체 동적 응답을 따로 비교한다.

그다음 필요성이 확인된 항목부터 pitch damping·엔진 시간상수 등을 하나씩 비교한다. 여러 항목을 동시에 바꿔 원인을 구분하기 어려운 탐색이나 자동 최적화는 추가하지 않는다. 양력/추진 계수처럼 트림까지 바꾸는 항목을 비교할 때는 각 실행의 계산된 트림 입력도 함께 공개한다.

**완료:** 기준/변형 곡선을 같은 축에서 겹쳐 보고, 입력·형상·초기 조건의 차이를 확인할 수 있다. 실제 정확도가 개선됐다는 판정은 실측 근거가 없으면 하지 않는다.

## 당초 계획한 실행 명령

아래는 계획 당시 인터페이스 예시다. 현재 같은 경로의 도구를 구현했으며 확정된 옵션·실제 실행 결과는 [사용법](flight-tests.md)을 따른다.

```powershell
python scripts/run-flight-test.py --case elevator-pulse --reset-flight
python scripts/report-flight-test.py artifacts/flight-tests/<run-id>
python scripts/report-flight-test.py <baseline-run> <candidate-run>
```

진행 순서는 **카메라 빌드 마감 → 엘리베이터 시험 하나 → 기록/실패 처리 → 재현·독립 계산·보고서 → 다른 시험 → 단일 매개변수 비교**다. 각 단계가 실제로 실행 가능한 상태로 끝난 뒤 다음 단계로 넘어간다. 필요한 범위의 데이터가 없다면 미검증을 유지하며, 계수를 조정해 원하는 그래프 모양을 만드는 것을 완료 조건으로 삼지 않는다.

후속 구현 마감: 카메라 빌드/실행, 기록/보고서, 재현/독립 계산, 9종 시험, Iy ±10% 비교, Thor 회귀를 완료했다. 최종13회15,013개 표본과 최초 실패 기록을 보존했다. 사용자의 완료 후 종료 지시에 따라 Unreal/API/보조 프로세스는 종료했다. 상세 수치·발견한 한계는 사용법의 실제 실행 기록을 따른다.
