# 연속 귀환·착륙과 기체 동작 개선 계획

2026-11-18 사용자 우선순위 변경을 반영했다. **이 문서는 최초 계획·수정 전 진단 기록이며, M0~M5 연구 범위의 구현과 실제 결과는 [완료 기록](return-landing-results.md)을 따른다.** 일반 항로점 포착 개선, 이상적 선회식 잔차6.2%의 원인 분석, 일반 러더 협조 제어는 뒤로 미룬다. 우선 범위는 **자동착륙 전환 수정 → 실제 Unreal 지형의 연속 왕복 → 추진·형상·지상 물리 개선과 변경 후 시연**이다.

| 단계 | 실제 상태 |
| --- | --- |
| M0 | 단계·거절 이유·목표/실제값·WGS84 참고 경로 UI/API/CSV 구현 |
| M1 | 귀환/형상/정렬 단계, 연속 경로, 목표 변화율·복행 제한 구현. 코어 고고도/반대 기수 회귀 통과 |
| M2 | 실제 제주 가상 활주로에서 한 번 초기화한 이륙→임무→귀환→주차와 장면 기록 확보 |
| M3 | 치수/접촉 정합·플랩/프로펠러/바퀴 표시, 추력선 모멘트·트림·동력 한계 검사 완료 |
| M4 | 기체별 마찰/충돌 기준·조향/제동 응답, 실제 출력 공개. 완충 추가를 요구하는 튐은 재현되지 않아 강체 접촉 유지 |
| M5 | 개선 전후·작은 바람·20km 높은 임무 연속 주차, 개발 검사·비교 그래프·문서 갱신. 실제 성능 검증은 별도 |

기존 연구 모델·실제 완료 범위는 [C208B 안내](c208b-research.md), [시험 기록](flight-tests.md)을 따른다. 실측 자료가 없는 값은 계속 연구 가정으로 표시한다. 눈에 보이는 진척을 우선하되 조종면 표시·위치·접지 결과가 같은 자체 물리를 따라야 한다.

## 1. 이번 확인 결과

실행 중인 Unreal에는 상태 조회만 했고 입력·초기화·일시정지·종료를 보내지 않았다. 최초 조회 시점은 자동이륙 `rotate`였으므로 사용자가 본 착륙 진동의 현장 로그를 확보한 것은 아니다.

별도 표준 C++ 진단 프로그램에서 **현재 연구 프로필과 현재 제어기·비행역학**을 그대로 사용했다. 평평한 가상 지면·무풍·TAS65m/s·접근 목표40m/s·제어 간격.01초다. 실제 지형 재현이나 새 제어기 성능 시험이 아니다. [진단 소스](../artifacts/landing-diagnosis/probe.cpp), [출력](../artifacts/landing-diagnosis/diagnosis.csv), [저고도 시계열](../artifacts/landing-diagnosis/low_aligned.csv).

| 사례 | 관측한 결과 | 의미 |
| --- | --- | --- |
| 활주로 기준 높이2600m, 측방/종방향 각각5km | 착륙 시작 거절 | 현재 높이 제한10~1000m. 원거리·고고도 임무에서 돌아오는 운항 단계가 없음 |
| 높이800m, 측방/종방향 각각5km | 시작은 수락, 첫 유도 명령 생성 실패 | 실제 플랩0° 상태에서 목표40m/s의 level trim을 구하지 못함 |
| 높이500m, 반대편 측방5km·종방향5km·반대 기수 | 같은 첫 명령 실패 | 특정 진입 방향 하나의 문제에 국한되지 않음 |
| 활주로600m 전·높이60m·기수 정렬, TAS65m/s | 첫 명령은 final/플랩30°. 8.31s에 복행, 36.21s에 join. 180s 후에도 join, 최대 에일러론 명령 절댓값25° | 고속→착륙 전환을 준비 없이 시작하면 정상 착륙을 완료하지 못하는 사례 재현 |

별도 [트림 가능성 대조](../artifacts/landing-diagnosis/trim-feasibility.csv)에서도500/800m의40m/s·플랩0°는 불가능하고, 플랩10°/30°에서는 가능했다.2600m에서는10°도 불가능하고30°에서 가능했다. 이는 현재 연구 계수에 대한 계산 결과이며 실제 C208B 운용 한계가 아니다. 플랩 전개가 끝나기 전에 목표 속도를 먼저 낮추는 전환 오류를 직접 확인한 근거다.

마지막 사례의 에일러론 명령은180초 동안1°를 넘는 부호 반전이11번 있었다. 이는 소음 구분용 진단 집계이며 성능 허용오차가 아니다. 모든 반전이 불필요한 진동이라고 단정하지 않는다. 특히 후반의 반복 반전과 항로점 미진행을 경로/뱅크 목표 로그로 구분해야 한다. 화면에서 사용자가 본 현상과 동일 원인임은 아직 확정하지 않았다.

### 코드로 확인된 문제 구조

1. **귀환과 착륙 접근이 한 단계다.** [FlightOperations.h](../Source/FlightCore/FlightOperations.h)의 `join()`은 착륙 시작 직후80m/접근 속도의 사각 항로를 만든다. C208B 40m/s일 때 측방 약1773m, 후방 약5319m 등의 경로다. 높은 임무 고도에서 이 경로로 전환할 에너지·고도 처리 단계가 없다.
2. **형상 준비보다 목표 속도가 먼저 바뀐다.** `update_flight_operation()`은 landing의 대부분 단계에서 최대 플랩30°를 명령하지만 실제 전개에는 시간이 필요하다. 동시에 `guide()`는 현재 실제 플랩각으로 새 목표 TAS의 수평 트림을 계산한다. 현재 형상에서 불가능한 저속 목표를 먼저 주면 첫 제어 출력 자체가 실패할 수 있다.
3. **항로점 통과에 고도·속도가 묶여 있다.** [Navigation.h](../Source/FlightCore/Navigation.h)는 수평 접근뿐 아니라 고도±15m·속도±2m/s를 함께 만족해야 통과한다. 점에 먼저 도착하고 감속/강하가 늦으면 반복 포착 시도가 생길 수 있다. 일반 포착 로직 전면 수정은 보류하고 착륙 전용 진입 경로에서 이 조건을 만족하도록 준비한다.
4. **접근·복행 전환 때 목표와 제어기 메모리가 불연속적이다.** 새 Navigation 생성, 속도/높이 변경, 최종 접근의 이동 가상 목표점을 사용한다. 경로 목표·뱅크 목표·적분 상태를 기록해 전환 직후의 포화와 흔들림을 확인해야 한다. 특히 `track()`의 내부 가상 높이는 강하율 feedforward용이며 화면에 그릴 실제 경로가 아니다.
5. **현재 명령 거절 사유가 불명확할 수 있다.** [serve-api.py](../scripts/serve-api.py)는 실패 시 기존 운항 message를 오류로 반환할 수 있다. 실제로 착륙이 수락됐는지부터 분리해 보여 줘야 한다.
6. **실제 지형과 활주로 기준 높이가 다르다.**80m의 활주로 기준 높이는 귀환 경로 전체의 지형 이격을 보장하지 않는다. 현 제어기는 장애물·지형을 회피하지 않는다.
7. **외형의 지상 크기가 맞지 않는다.** [FlightGround.cpp](../Source/UAVSim/FlightGround.cpp)는 기체별 바퀴 위치를 적용하지만 표시 바퀴 반지름 약3cm·지지대 길이11cm는 [기존 생성 값](../Source/UAVSim/FlightScene.cpp)이 남아 있다. C208B급 외형에서 바퀴가 작거나 지지대가 동체와 떨어져 보일 수 있다. 이는 에일러론 명령 진동의 원인과 별도로 다룬다.

| --- | --- | --- |
| M0 | 착륙 전환 진단·명령 접수/거절 표시 | 요청한 명령과 실제 운항 단계, 거절 이유, 목표/실제 속도·형상이 명확히 보임 |
| M1 | 귀환→감속/강하→정렬→최종 접근 분리 | 멀리서 착륙을 인가해도 복귀 단계와 경로를 따라 비행하고, 최종 접근에서 반복적인 과대 뱅크/조종면 포화가 줄어듦 |

각 행을 실행 가능한 작은 단위로 끝낸 뒤 다음 행으로 간다. 모든 물리를 먼저 개편한 뒤 마지막에 화면을 확인하는 순서로 잡지 않는다.

## 3. M0 — 진단과 화면 상태

- 기존 상태·CSV에 필요한 항목만 추가한다: 착륙 요청 수락 여부/거절 코드, 단계 전환 이유, 활성 복귀 구간, 목표 코스·뱅크·TAS·강하율, 실제 자세/속도, 조종면 명령/실제각, 플랩 명령/실제각, 항로/활주로 횡오차.
- 같은 상황에서 **경로/뱅크 목표가 흔들리는지 → 뱅크 목표는 안정적인데 제어 출력이 흔들리는지 → 실제 조종면·화면만 다른지**를 순서대로 구분한다. ±180° 코스 오차의 방향 전환, 조종 포화, 실속 회복 개입, 적분 잔류도 기록한다.
- 초기 비교는 현재 제어기를 그대로 기록한다. 실제 사용자 임무와 가까운 출발 위치·고도·속도·기수·바람·활주로를 먼저 고정하고 같은 프로필 지문으로 재현한다.
- Web UI/HUD에 `귀환 중 / 고도 처리 중 / 감속 중 / 접근 정렬 / 최종 접근 / 복행 / 착륙 활주 / 주차` 등 실제 운항 상태를 표시한다. 명령 거절은 기존 운항 진행 문구와 별도로 이유를 보여 준다. 필요한 정보만 표시한다.
- 경로 표시는 활주로 중심선·접근 진입 지점·승인한 귀환 경로부터 한다. 내부 제어용 가상 목표점이나 수식 변수를 실제 비행 경로로 표시하지 않는다. 지도 편집기는 추가하지 않는다.

**완료:** 사용자와 개발자가 같은 단계·경로·명령 수락 상태를 보고 원인을 구분할 수 있다. 착륙 실패를 정지/복행/거절 중 무엇으로 처리했는지 기록한다.

## 4. M1 — 자동착륙 전환 수정

기존 `FlightOperations`에 필요한 단계만 추가하고 같은 비행역학·작동기·지면 접촉을 사용한다. 위치나 자세를 경로 위로 직접 옮기지 않는다. 일반 임무 항로점 포착 알고리즘·러더 협조의 별도 개선은 착수하지 않는다. 공통 제어 코드 수정이 반드시 필요하면 착륙 문제와 연결되는 최소 변경만 하고 Thor/기존 항법 회귀를 확인한다.

### 귀환과 에너지 처리

- 착륙 인가는 곧바로 저속 최종 접근을 의미하지 않게 한다. 현재 TAS/형상에서 가능한 트림·제어 입력을 유지하며 **귀환 → 필요한 강하/고도 처리 → 접근 진입 → 감속·플랩 → 최종 접근**으로 전환한다.
- 새 명령 준비 시 현재 위치·고도·속도·선회 가능한 반경·예상 감속/강하 거리와 접근 지점까지의 여유를 확인한다. 부족하면 별도의 고도 처리 구간/대기 경로를 설명하고 수행한다. 직선 귀환 한 번에 과도한 고도 손실을 강요하지 않는다.
- 목표 속도/강하율은 단계별로 연속 전환한다. 플랩은 단계·속도·실제각·유효 트림 조건을 함께 확인해 전개한다. 실제 VFE 자료가 없으면 선언한 연구 시험 범위로 제한하며 실제 C208B 운용 한계라고 부르지 않는다.
- 최종 접근 길이는 접근 고도·연구용 경사·정렬/감속 시간으로 정한다. 기존600m를 모든 기체/진입 조건에 재사용하지 않는다. 예를 들어3°를 선택하면 개발 시연 조건임을 명시하고 실제 기체 절차로 표현하지 않는다.
- 부적합한 속도/형상 트림을 요구하여 유도 명령이 사라지는 진단 사례를 먼저 없앤다. 파일/실제 지원 범위로 유효한 중간 상태가 없으면 명확한 거절/실패 사유를 반환한다.

### 접근의 좌우 흔들림

- 착륙 구간은 활주로 연장선·정렬 구간이라는 연속 경로를 추종하도록 한다. 급한 사각 모서리·짧은 점 포착에 최종 접근을 의존하지 않는다.
- 현재 진행 방향과 가능한 선회 반경으로 진입 구간을 선택하고, 거의 정반대 방향에서 좌/우 선택이 매번 바뀌지 않도록 필요한 방향 유지 조건을 둔다. 일반 경로 최적화 기능으로 확대하지 않는다.
- 코스/뱅크 목표의 급변 제한, 단계 전환 시 메모리 이관/초기화, 포화 중 적분 처리, 전이 조건의 히스테리시스는 **로그에서 확인된 원인에 해당하는 것만** 적용한다. 처음부터 모든 이득을 낮추지 않는다.
- 직선 접근의 완료 기준은 에일러론이 전혀 움직이지 않는 것이 아니다. 경로 오차·뱅크 목표가 안정된 뒤 지속적인 큰 반전/한계 포화가 남지 않고, 접근 정렬·속도·강하 조건을 만족하는지 확인한다.
- 플레어 진입은 CG 높이·바퀴 접촉 치수·강하율·전진속도와 연결한다. 복행은 추진/형상/속도 회복 단계로 처리하고 반복 횟수·이유를 공개한다. 무한 합류/복행 반복 대신 제한된 재시도 후 명시적 대기/중단 상태를 둔다.

**완료:** 진단에서 거절된 고고도 요청은 지원 범위 안에서 귀환 절차로 들어가거나 정확한 이유로 거절한다. 첫 명령 실패·고속 즉시 플랩 전개·준비 없는 저속 전환을 회귀 사례로 남기고 고친다. 실제 지형 연속 왕복으로 이어질 수 있는 진입/복행 절차가 동작한다.

## 5. M2 — 실제 Unreal 지형의 첫 연속 왕복

기존 대한민국 지형과 제주2000×60m **가상 시험 활주로**를 사용한다. 실제 제주공항 절차 검증이 아니다. DTED/지도 교체·공항 데이터 확장은 하지 않는다.

- 한 번의 지상 초기화 뒤 이륙→임무 구간→착륙 인가→귀환→접지→주차를 이어간다. `prepare-landing`·위치 재설정·재읽기를 중간에 사용하지 않는다.
- 대표 임무는5/10/20km에서 선정하고, 서로 다른 기수와 고도를 배정한다. 첫 후보는5km/500m,10km/1500m,20km/2600m이며 높이는 WGS84 타원체고다. 실제 경로/지형·지원 범위 검토로 확정한다. 첫 성공 사례 하나 뒤 나머지로 넓힌다.
- 모든 기체 위치/귀환 구간/선회가 계산 원점50km 범위와 유효 지형 범위 안에 있어야 한다. 현재 접근 거리 약11.1km/높이1000m의 거절 기준을 단순 삭제하지 않고, 귀환 경로 준비 조건과 단계별 한계로 대체한다.
- 선택한 시험 경로의 지면 높이·지형 누락과 여유 고도를 사전 검사한다. 지형 이격 기준은 명시한 개발 값으로 둔다. 누락 구간/충분하지 않은 여유는 거절한다. 이는 선정한 시연 경로 검사이며 전국 자동 지형/장애물 회피 기능이 아니다.
- 맵과 기체 기준 좌표 변환, 활주로 기준 높이·실제 지면 AGL·WGS84 높이를 구분한다. 실제 접지·바퀴 반력·주차 완료를 기록한다.
- 현재 메인 카메라와 CCD를 유지하고 승인 경로·단계·목표/실제 속도·플랩을 함께 보여 준다. 장면 캡처는 API로 수행하고 브라우저/UI 자동화는 하지 않는다.

**완료:** 선정한 실제 지형 경로에서 중간 위치 초기화 없이 주차까지 성공한 한 번의 연속 기록과 장면 증거를 먼저 남긴다. 정상 진입뿐 아니라 부적합 접근의 복행/중단도 구분한다. 무풍 성공 뒤 기존 지원 범위의 작은 바람 사례를 추가한다.

## 6. M3 — 추진·형상 개선

### 먼저 보이는 형상 정합

- C208B 연구 외형의 동체/날개/꼬리·프로펠러 위치·고정기어·바퀴/지지대 크기를 한 구성으로 맞춘다. 먼저 기존 부품/메시로 가능한 연구용 외형을 개선하고 실제 C208B CAD라고 부르지 않는다.
- CG·기체 축·표시 치수·물리 접촉점을 대조한다. 바퀴 위치만 맞추고 지지대/바퀴 크기를 그대로 남기는 문제를 고친다. STL 입력이 물리 형상이나 조종면을 자동 생성하는 것으로 확대하지 않는다.
- 플랩 메시/힌지는 실제 플랩각, 조종면은 실제 작동기 각도를 따라 표시한다. 바퀴 회전은 이동 거리와 표시 반경에 맞춘다. RPM 물리가 없을 때의 프로펠러 회전은 표시 애니메이션임을 구분하며 실측 RPM을 만들어 공개하지 않는다.

### 단발 추진 수식 보강

- 기존 동력 상한·정지 추력·밀도비·스풀 가정을 표/곡선으로 점검하고 모델 출처·유효 범위를 갱신한다. 추력선의 CG 상대 위치에 따른 모멘트부터 같은 강체 식에 연결한다.
- 실제/연구용 근거를 확보한 CT/CQ·전진비/RPM 자료가 있으면 해당 범위의 추력·토크와 응답을 단계적으로 추가한다. 자료가 없으면 개발 가정을 표시하고 동력·단위·정지/전진 한계의 계산 검사를 먼저 완성한다.
- 프로펠러 후류·거버너·리버스·페더링을 한 번에 추가하지 않는다. 화면 회전만으로 실제 추진 정밀화가 끝났다고 표시하지 않는다. 쌍발 배열/엔진 플러그인도 만들지 않는다.
- 플랩별 양력·항력·피칭 모멘트와 추진 변화는 트림/수동 응답·이착륙 결과를 함께 확인한다. 원하는 화면을 만들기 위해 계수를 임의 보정하지 않는다.

**완료:** 표시 형상·실제 형상 상태·접촉 기준이 일치하고, 추가한 추진 항목마다 출처/가정·수식·개발 검사와 기존 모델 대비 결과가 있다. 실측이 없는 항목은 미검증으로 유지한다.

## 7. M4 — 지상 물리 정밀화

- 구름 저항·제동·횡마찰·조향 응답과 속도별 조향 제한을 기체 설정으로 분리한다. 기존 Thor 기본값과 실패 보존 계약을 유지한다.
- CG 하중 분배·주륜/전륜 접촉·기수 내림·제동 시 피칭을 점검한다. 필요성이 재현된 경우 각 바퀴 위치의 지형을 따로 조회해 코어에 명시적으로 전달한다. 코어 안에 Unreal 지형 조회를 넣지 않는다.
- 완충이 필요한 튐을 확인하면 기존 접촉 해법과 일관된 최소 압축/감쇠를 추가한다. 반력과 완충력을 중복 적용하지 않고 에너지·침투·평형을 검사한다. 지지대 표시도 같은 압축 상태를 사용한다.
- 접지 허용 조건·충돌 기준과 표시를 분리한다. 평균 반력은 최대 착륙장치 하중이 아니다. 실제 타이어/완충 자료가 없으면 연구 가정으로 기록한다.

**완료:** 정지 평형, 활주·조향, 제동, 낮은 강하 접지, 경계/경사/누락 지면 사례를 확인한다. 접지 후 비정상 침투·튐·바퀴/동체 표시 불일치가 남으면 성공으로 표시하지 않는다.

## 8. 검사와 마감

- M0/M1: 고고도 거절·현재 형상에서 불가능한 목표·고속 접근·180° 반대 기수·단계 전환·복행의 작은 코어 검사부터 둔다. 목표/실제 뱅크·조종면·횡오차·실제 TAS/플랩을 비교한다. 정상적인 선회에 필요한 조종면 반전까지 실패로 취급하지 않는다.
- M2/M5: 실제 Unreal의 연속 왕복을 기존 기록기/API로 기록하고 단계·경로·접지 장면을 보존한다. 원본/변형 프로필·간격·바람·실패 이유를 함께 남긴다. 처음 실패한 조건을 쉬운 조건의 성공으로 덮어쓰지 않는다.
- M3: 추력/토크·모멘트 팔·동력 상한·플랩 공력·표시 축/치수·작동기 실제각을 해당 변경마다 확인한다.
- M4: 반력/중량 평형·마찰의 비양의 일·제동의 단순 독립 기준·완충 에너지·시간 간격 영향을 확인한다. 실측 착륙거리 허용오차를 임의로 만들지 않는다.
- 허용오차는 구현 전에 해석 근거와 개발 운용 범위로 정한다. 진단에서 측정한 진동/포화 시간·경로 오차를 기준으로 개선을 비교하고 실제 C208B 성능 합격 기준과 구분한다.
- 공통 코어를 바꾸면 관련 CTest, Unreal 경계를 바꾸면 Development 빌드와 실제 API 검사로 진행한다. 변경이 없는 지도/EOIR/워게임 전체 검사를 반복하지 않는다.
- API 상태/거절 이유/단계가 바뀌면 endpoint·Python 클라이언트·해당 Web UI·[API 매뉴얼](api-reference.md)·기록기를 같은 작업에서 갱신한다. 기본 카메라·CCD 운용·Thor·기체 재읽기 실패 보존을 회귀 확인한다.

최종 마감은 **고친 착륙 전환 + 실제 지형 연속 왕복 + 정합된 외형/추진/지상 동작 + 개선 전후 보고서**다. 실측 자료 확보와 정식 성능 시험은 별도 후속 작업이다. 일반 근접 항로점 포착·선회식 잔차 분석·러더 협조 제어는 이 순서 이후에 다시 다룬다.
