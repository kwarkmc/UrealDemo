# IGManager 사용 범위와 UAVSim API 비교·추가 구현 후보

2026-11-19 사용자 제공 자료와 현재 UAVSim 코드에 근거한 조사다. 사용자는 SimConnect 전체를 그대로 복제하려는 의도가 없다고 명시했다. 이번 요청은 연구 자료의 TrashCan 인계이며, 아래 후보의 구현 승인이나 기능 완료를 의미하지 않는다.

## 근거와 적용 범위

- 사용자 원문: [API 노출 표면](research/igmanager/simconnect-api-surface.md), [데이터·이벤트·객체 상세](research/igmanager/simconnect-data-detail.md). 두 첨부의 내용을 수정하지 않고 보존했다. [원본 식별·해시](research/igmanager/sources.json).
- 현재 제품 계약: [API 매뉴얼](api-reference.md), [HTTP 서버](../scripts/serve-api.py), [Python 클라이언트](../uavsim_client.py), [기체 초기화](../Source/UAVSim/FlightScene.cpp), [최신 항법·추진·지상 상태](navigation-physics.md).
- 별도 참고: [SimConnect v6 공개 SDK 조사](simconnect-reference.md). IGManager 자료는 **P3D v5 운용·managed wrapper v4.4.0.0 참조**라고 보고하므로 v6 항목 수/바이너리 계약을 그대로 적용하지 않는다.

IGManager 원본 저장소·DLL·실행 환경은 이번 조사에서 직접 검증하지 않았다. 첨부 자체도 text-search 기반이며 일부 필드 수/소비 여부가 불완전하다고 명시한다. managed 메서드와 native export의 대응, 특히 기상 래퍼 추정은 확정 사실로 사용하지 않는다. 이벤트 enum/매핑 존재와 능동 호출·실제 소비를 구분한다. 첫 자료의 자기관 요청11개 설명과 상세 자료의10개(유효8+orphan2) 등 집계 차이는 원문대로 남기며 요구사항 개수로 확정하지 않는다.

## 핵심 차이

IGManager는 여러 항공기·지상 객체·표적·카메라를 관리하고 상태를 주고받는 운용을 사용한다. UAVSim은 한 기체의 자체 비행역학·수동/자동 운항·명시적 시간 진행 실험에 집중한다. 비슷한 연동을 위해 가장 큰 추가 작업은 **객체별 제어, 초기화 없는 연속 상태 주입, 텔레메트리 전달 계약**이다.

## 이름만 변환하면 안 되는 의미 차이

### 연속 pose와 초기조건

현재 /pose는 SetAircraftGeodetic → SetInitialCondition → InitializeFlight로 연결된다. 계산 원점·속도 구성·각속도·자동 운항 등을 다시 만들고 정지한다. 외부 궤적을 매 주기 넣는 통로로 반복 사용하면 비행이 계속 초기화된다.

외부 상태를 수용한다면 자체 비행역학 객체와 외부 상태로 표시하는 객체를 구분하고 전환·초기화 규칙을 명시해야 한다. 같은 위치/자세를 두 계산 주체가 동시에 갱신하지 않는다. 기존 수동/자동항법의 자체 비행역학 경로는 유지한다. 입력 시간·좌표/속도/자세·유효성·입력 중단 시 동작을 계약으로 정한다. 이는 제안이며 현재 external-state API가 있다는 뜻이 아니다.

### 다중 표시 객체와 다중 물리 기체

자료에는 항공기5슬롯·지상객체20슬롯이 보이나 자체 비행역학5대가 반드시 필요한 것은 아니다. 외부 좌표를 표시하는 용도라면 객체 관리·pose 갱신부터 가능하다. 각 기체가 독립적으로 비행해야 한다면 계산 상태·입력·프로필·항법을 각각 가져야 한다. 정적 tank/missile/marker, 워게임 선형 연출을 이동 표적/다중 기체로 간주하지 않는다.

### 텔레메트리의 시점·종류

필요 갱신 주기가 충족되면 기존 HTTP를 주기 조회하는 어댑터로 시작할 수 있다. 프레임 동기나 고정 지연 요구가 확인되지 않았는데 새 스트리밍 서버부터 만들지 않는다. 객체 ID·표본 시뮬레이션 시간·순번·유효성을 정의하고 여러 시점의 값을 같은 표본처럼 합치지 않는다. VISUAL_FRAME interval5는5Hz가 아니다. UAVSim 상태 JSON은 센서 오차/지연을 모사한 측정값이 아니라 계산 상태다.

### 모델과 단위

프로펠러RPM을 터빈N1로 대체하거나 미지원 연료량을 정상0으로 반환하지 않는다. 미적용 값은 지원/유효성 정보와 함께 다룬다. 현재 dynamic_propeller=false에서RPM/토크0의 기존 계약도 구분한다. 혼합비·프로펠러 레버·combustion 상태를 받는 것과 혼합비/거버너/시동 모델 구현은 다르다. 단순 표시만 지원한다면 그렇게 명시한다.

ft↔m·kt↔m/s·deg↔rad 외에 IAS/TAS, MSL/AGL/타원체고, 세계축/FRD, PBH 순서/부호, 기상 풍향/ENU 바람의 의미를 확인한다. 첨부에 수직 기준이 확정되지 않은 Altitude는 WGS84로 추정하지 않는다.

## 권장 구현 순서와 종료선 — 아직 미착수

1. **소비 계약 확정**: 실제 화면·유도·로그가 읽는 필드와 능동 호출 명령을 추린다. 원본 icd-sim-api-v1.md/vendor-requirements.md, 호출부에서 주기·단위·비트/enum·오류·미지원 표현을 확인한다. 종료선은 실제 소비 기능의 RX/TX·단위·지원 여부 대응표다.
2. **기존 기능 어댑터와 운동 데이터 공개**: 기존 위치·자세·속도·각속도·조종·기어·시간·추진을 연결하고 필요한 축별 속도/가속도를 공개한다. 종료선은 같은 표본의 단위/축 변환 및 미지원/오류 전달 검사다.
3. **객체 관리·연속 상태 입력·카메라**: 생성 → 초기화 없는 위치/자세 갱신 → 상태조회 → 추적 → 삭제를 작은 실행 기능으로 완성한다. 필요한 경우에만 다중 물리 기체로 확대한다. 종료선은 ID별 독립성·제어 주체·삭제/입력중단 처리·시점 연계다.
4. **실제 필요한 계통 확장**: AP 목표 유지·차등 제동·등화·연료·추진·기상을 소비 우선순위대로 추가한다. 물리 모델은 [후속 물리 계획](physics-expansion-plan.md)과 연결하고 데이터/수식/검사 없이 필드만 채워 완료 처리하지 않는다.

첫 개발 후보는 기존 상태 연동·운동 데이터 공개, 다음은 다중 표시 객체·연속 상태 주입·객체 추적이다. 사용자 요청 없이 SimConnect DLL/ABI 복제·플러그인 체계·전체 이벤트 서버를 만들지 않는다. 대외에 ICD만 노출한다는 IGManager의 vendor split 구상은 첨부의 방향이며 UAVSim에서 확정/구현된 통신 규격이 아니다.

## 그대로 재현하지 않을 항목

- orphan AVIONICS/LG 요청2개, 소비자 없는 observer 조회, 미사용 그룹6개, 데드 AP_VERTICALSPEED 정의를 요구사항에 자동 포함하지 않는다. 실제 수직속도 TX는 자료상 VERTICAL_SPEED다.
- TargetId→SURFACE TYPE, SpeedTas→AIRSPEED INDICATED라는 기존 매핑을 새 API 의미로 가져오지 않는다. 기존 프로그램의 의존성이 확인될 때만 호환 어댑터에 한정한다.
- enum에 나열된 AP/FBW/항법/패널 이벤트 전체가 실제 필요하다고 단정하지 않는다. 사용하지 않는 고급 기능을 이번 인계로 구현 승인한 것으로 해석하지 않는다.
